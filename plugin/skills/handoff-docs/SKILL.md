# 寫給後續 AI 的文件

AI 寫給下一個 AI 看的文件，讀的人沒有你現在的對話記憶，只看得到文件本身。
好文件的標準：下一個 AI 不用重建隱藏脈絡，就知道要達成什麼、誰說了算、哪些有證據、怎樣算完成、什麼時候該停。

## 先決定放哪裡

| 內容 | 放哪 |
|---|---|
| 每次都要知道的事實和規則 | Codex 原生 `AGENTS.md`；Claude Code 原生 `CLAUDE.md`，可用 `@AGENTS.md` 匯入共用規則；位置與載入範圍見 skill `project-docs` 的官方依據 |
| 偶爾才用的流程、長清單 | skill（`%USERPROFILE%\.claude\skills\<名稱>\SKILL.md`），需要時才載入 |
| 非做到不可、不能靠自覺的事 | `settings.json` 的權限規則或 hook，不要只寫在文件裡 |
| 只在特定時機才該想起的提醒 | hook，但要「有事才出聲」：沒問題就完全不輸出、同一件事每個工作階段只講一次、訊息壓到一行。每次都講的提醒會變成背景雜訊被自動忽略 |
| 一次性的工作計畫、進度 | 專案內的計畫檔，做完移到資源回收筒 |
| 發生過什麼 | git commit 或操作紀錄，不寫進 CLAUDE.md |
| 使用者偏好、對 AI 的糾正 | memory |
| Codex 要讀的規則 | `AGENTS.md`；CLAUDE.md 用 `@AGENTS.md` 引用共用 |

專案內的 HANDOFF、ROADMAP、decisions、specs 放哪照 skill `project-docs`。

修改既有文件時，受版本控制或專案文件制度內的檔案，請照制度在原路徑覆寫並保存規定紀錄；其餘才另存新檔保留原檔。修改範圍仍依使用者授權。以下「取代舊規則」適用於已授權維護的制度內文件。

## 寫 CLAUDE.md / 規則檔

- 每份少於 200 行。每行都問：「刪掉這行，下一個 AI 會不會出錯？」不會就刪。
- 只寫猜不到的：非預設的指令、跟一般習慣不同的規則、踩過的坑、環境怪處。
- 不寫：看程式碼就知道的、逐檔說明、長篇教學、很快會過時的狀態。
- 規則要能檢查：寫「送出前執行 `npm test`」，不寫「記得測試」。
- 模糊詞的判斷標準：兩個 AI 讀了會做出實質不同的事，就要換成可檢查的條件或寫明誰決定。清單見下方「模糊詞清單」。
- 會改變範圍、花費、權限、共用資料、架構的規則，寫明誰決定（通常是使用者）。
- 附上原因（「因為以前發生過 X」）。知道原因，AI 才能在規則沒寫到的情況下判斷。
- 改寫示範：「不要亂改、不要猜、不要重跑」→「只改任務指名的檔案；證據不足時標「未驗證」並說明缺什麼；同一個錯誤修兩次仍失敗就停下交回」。
- 不用全大寫或「務必」「絕對」加強語氣。一條規則一直被忽略時，改的是它的位置、順序與周圍篇幅，或改由 hook、腳本檢查、錯誤訊息強制執行；強調很多行等於沒有一行突出。
- 管得多緊看風險：研究類給目標、證據標準、停止條件，方法讓它自己選；例行實作給偏好做法和不能破壞的條件；花錢、動共用資料、難復原的動作要寫範圍、驗證、誰同意、失敗怎麼停或回滾。
- 改之前先讀整份，不要跟現有規則矛盾；矛盾時 AI 會隨機挑一條。取代舊規則時直接刪掉舊的（要留紀錄就寫進 CHANGELOG 或 decisions），不要讓兩個版本同時有效。
- 不寫「最新真相」「以此為準」這類標籤：每份文件都這樣寫，就有好幾個「最新真相」。判斷哪份是現行靠「一件事只在一個檔案」。
- 不在文件裡放很快過時的數字快照；寫查詢方法或工具路徑。
- 規則是從錯誤長出來的：AI 重複犯錯才加一條，不要預先寫一堆。

## 分清事實的種類

文件裡這幾種要看得出差別：專案事實、實際觀察到的、推論、指示、已做的決定、未解問題、歷史。
- 這次工作階段遇到的限制（例如某工具沒權限），不要寫成整個專案或整個平台的限制。
- 沒跑過的驗證寫「未驗證」，不寫成通過。
- 不為了消除措辭模糊而發明領域規則；不知道就標成待使用者決定。

## 寫交給 Codex、subagent 或下一個工作階段的指示

對方什麼都不知道，要當成交給一個聰明但剛來的同事。包含這五件事：

1. 目標：要做成什麼，以及為什麼。
2. 背景：相關的檔案路徑、錯誤訊息、已經試過什麼。
3. 限制：可以改哪些範圍、不能碰什麼、要用什麼語言回報、回報多長。
4. 完成標準：怎樣算做完，要拿什麼證據（執行了哪個指令、結果是什麼）。
5. 停止條件：遇到什麼要停下交回，而不是自己決定（例如需要改共用設定、需要使用者同意、證據不足）。

- 給目標，讓它自己想細節，不要一步一步規定。只有流程本身是要求時才列步驟。
- 不要要求它邊做邊回報，它可能做到一半就停。
- 要它標出「查不到、沒驗證」的部分，不要硬編。
- 派工與驗收的做法照 skill `codex-dispatch` 與 `maker-checker`。

## 寫計畫書 / 交接單

- 開頭一句話講目標和目前進度。
- 已完成的項目附上驗證方式，未完成的寫清楚下一步。
- 寫出「第一個可以直接執行的動作」，下一個 AI 不用重讀整段歷史就能開工。
- 卡住的事寫：影響什麼、擋不擋路、已有什麼證據、誰要處理、下一個驗證動作。
- 列出已知的坑和做過的決定（含原因），避免下一個 AI 重新爭論。

## 寫 skill

- `description` 決定會不會被載入，body 是載入後才看得到。「何時使用」只寫在 description，body 裡寫沒用。
- description 描述情境，不只寫術語：寫「用在…，包含使用者沒講名字但在描述…的情況」，讓 AI 從問題推斷。
- 只有真的會搶錯的近鄰才寫排除邊界。
- 一個 skill 一個意圖族。description 讀起來像「A、B、C、D 功能清單」且各自用語不同，就拆開；已有 skill 涵蓋同一類意圖，併進去。
- SKILL.md 放核心流程（少於 200 行），條件性細節放同資料夾的其他檔案，在 SKILL.md 用相對路徑指過去。

## 模糊詞清單

出現時檢查：兩個有能力的讀者會不會因為沒有標準或決策者而做出不同的事？會就改。

- 中文：合理、適當、必要時、視情況、酌情、盡量、最好、原則上、可行時、適度、充分、重要、相關、差不多、先做能做的
- English：reasonable、appropriate、as needed、if necessary、where possible、best effort、sufficient、relevant

改法例：
- 「測試差不多就好」→「完成前執行 `npm test` 與 `npm run build`，結束碼都是 0」
- 「必要時可以改共用設定」→「需要改共用設定時，寫成需求交回，由使用者決定」
- 「先做能做的，卡住再說」→「只做 `src\parser\` 範圍內的事；同一個錯誤試兩次沒有新資訊就停，回報錯誤原文與你判斷的失敗層」

## 各類文件建議結構

- **規則檔（CLAUDE.md）**：角色與優先順序、目前的目標、決策規則與不變條件、與其他文件的介面。歷史放外面。
- **工作指示**：目標、需要的輸入、成功條件、範圍與限制、可寫入的範圍、停止與交回條件。
- **研究任務書**：核心問題、什麼證據能改變答案、偏好的證據來源順序（官方文件、原始碼、其他）、資料日期要求、已知事實與假設、查不到時怎麼標、停止條件、要交付的輸出。方法保持自由。
- **狀態回報**：結果與影響、關鍵證據或數字、剩下的問題、擁有者與下一步、從哪裡接續。
- **決策紀錄**：決定、考慮過的替代方案、理由、適用範圍或生效日、什麼情況要重新檢討。格式照 `project-docs` 的 `templates/decision.md`。
- **工具說明**：適用情境、輸入、副作用或權限、失敗時的行為、容易混淆但不該用它的相近任務。

## 寫完檢查

- [ ] 總行數合理（CLAUDE.md 少於 200 行）
- [ ] 沒有跟其他規則檔矛盾或重複
- [ ] 沒有過時資訊、沒有相對時間
- [ ] 模糊詞都有檢查標準或決策者
- [ ] 讀的人看得出目標、完成條件、停止條件
- [ ] 強制性的事用權限規則或 hook，不只靠文字
- [ ] 用另一個指令確認檔案真的寫進去了
