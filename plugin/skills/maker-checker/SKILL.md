# 做與驗分開

自己寫的東西自己檢查，會沿用寫的時候的假設，看不到自己漏掉的部分。驗收者不知道產出者的想法，只拿完成標準與實際產出核對，才能發現落差。不需要換模型，需要的是沒有前情。

## 角色

- 產出者：本對話、Codex 或 subagent。責任是交出可驗收的東西：檔案或 commit，加上完成標準與驗證指令。
- 驗收者：新的 Claude 對話、不帶前情的 subagent，或新的 Codex 任務。責任是核對、找出問題、回報證據；不修改產出。
- 修正由產出者做。驗收者同時修改會讓「誰改了什麼」失去紀錄，下一輪驗收也無從比對。

## 流程

1. 做之前先寫完成標準：可檢查的條件、要執行的指令、預期結果。完成標準寫不出來，代表工作本身還沒想清楚，先釐清。
2. 產出者做完，寫成檔案或 commit，不留在對話裡。commit 訊息寫做了什麼。
3. 產出者寫驗收單（格式見下），只含完成標準、產出位置、驗證方式。不寫自己的結論，不寫「我認為沒問題」，不寫預期的答案。
4. 開驗收者：
   - subagent：Claude Code 內用 Agent 工具派出，prompt 就是驗收單。
   - 新對話：開新的 Claude Code 視窗，貼上驗收單。
   - 新的 Codex 任務：照 skill `codex-dispatch`，驗收單存任務資料夾的 brief.md，task.json 設 sandbox 為 read-only；以 `python dispatch.py 驗收任務` 派出。
5. 驗收者逐項回報：通過、未通過或未驗證，每項附證據。
6. 產出者讀報告：
   - 未通過的項目修正後，產生新的 commit，回到步驟 3 再驗一次。
   - 驗收者回報的事實有疑問時，自己抽查原始檔案，不直接採信也不直接駁回。
   - 同一項連續兩輪未通過，停下來，檢查完成標準本身是否有問題，必要時問使用者。
7. 全部通過才向使用者回報完成，並附驗收報告的位置。

## 驗收單格式

```markdown
# 驗收單：<名稱>

你是獨立的驗收者。沒有人告訴你這份產出做得好不好；你的工作是找出它哪裡不符合下列標準。
只讀不改。看不到證據的項目標「未驗證」，不要推測。

## 產出位置
<檔案路徑或 commit>

## 完成標準
1. <可檢查的條件>
2. <可檢查的條件>

## 驗證方式
- 執行：<指令>，預期：<結果>
- 打開 <檔案>，確認 <內容>

## 回報格式
每項一行：編號、通過 / 未通過 / 未驗證、證據（指令與輸出、檔案與行號）。
最後加一段：標準沒涵蓋、但你認為有問題的地方。報告 30 行內；失敗的輸出照貼。
```

## 依產出類型選驗證

| 產出 | 驗證方式 |
|---|---|
| 文件、規則、交辦 | 驗收者讀完回答「它要我做什麼」「哪裡互相矛盾」「哪裡有兩種讀法」；驗收單不透露期望的答案 |
| 程式、腳本 | 實際執行測試或範例輸入，看輸出；不採信寫程式的人說沒問題 |
| 資料整理、批次修改 | 抽樣核對原始資料與結果（至少 10 筆或總數的 10%，取大者）；核對筆數、總和、有無遺漏 |
| 對外寄送的草稿 | 核對收件人、金額、日期、附件與原始資料一致；語氣與事實分開檢查 |
| 高風險判斷（刪除、對外、架構） | 驗收單加一句「試著推翻這個結論」，並要求列出最可能出錯的三個地方 |
| 研究與調查 | 逐項對照必答問題；缺項請產出者補，不降低標準；「查無」類的結論另派人回原始資料查證 |

## 注意

- 驗收者跟產出者用同一份對話就失去作用。需要追問時，再開一個新的驗收者，或把問題寫進下一版驗收單。
- 驗收者看到的檔案要是產出者最後交出的版本；驗收進行中不修改產出，否則報告對應的版本不明。
- 例行的驗收用新的 Claude 對話或 subagent 即可。規格或架構定案前、進入不熟悉的領域時，才另外請 Codex 以不同模型獨立看一遍；做法是請它獨立建立問題全貌，最後才給它看你的方案請它批判。
- 驗收不是重做：驗收者找不到證據就標「未驗證」，由產出者補證據。
- 驗收報告存成檔案（`docs\reviews\` 或專案的 `inbox\`），HANDOFF 只記結論與位置。
